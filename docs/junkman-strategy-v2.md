## 可归因于 junk_man 的核心框架

1. **GEX 是结构主图，不是单独的涨跌预测。** 重点是现价附近的大节点、次级节点和当前局部 gamma 区域；total GEX 或 flip 不能替代局部结构。证据消息：`1512459251724058945`、`1512491952321335376`、`1513965739932123307`、`1525288914926174329`。
2. **先等价格接受或拒绝节点。** 开盘先观察；有效机会包括 K 线实体越过节点、随后回踩守住，或触及节点后明确拒绝反转。只凭节点存在不入场。证据消息：`1513912646599049438`、`1513937701097705655`、`1516451090462277764`、`1521897514989518948`、`1521930744446849055`、`1523014741591720018`、`1523783693544456254`。
3. **正 gamma 倾向减速、钉住和区间；负 gamma 倾向放大和加速。** 方向仍须由价格相对节点与 VWAP 的行为确认。付费频道中的个股案例反复使用“磁铁区内均值回归、接受区外后切换路径”的表达。
4. **目标和失效都来自结构。** 突破失败或确认 K 被破坏即止损；价格在次级节点/大节点前停滞可减仓或退出。趋势出现后把止损抬到保本。证据消息：`1513973665673380141`、`1516507876099756084`、`1513938676386631762`、`1524436605887185037`、`1513973820581613628`、`1521531293500838128`、`1521930744446849055`。
5. **Flow 是辅助证据，不是必要条件。** junk_man 的讨论顺序是异常流、GEX、日线/价格结构之间互相验证，也明确出现“没有大单仍可形成机会”的情形。证据消息：`1513965401451790547`、`1524152473604984893`、`1522631807793631273`。自动转发的 Flow 还需防延迟与重复：`1521183252763775058`。
6. **API 应形成证据链，而不是堆字段。** `api-mcp` 讨论强调直接读取 Heatmap、结合多日 OI 变化、Heatmap 和 Flow；并没有一套由 junk_man 发布的、可直接复制的完整 API 自动交易公式。证据消息：`1535262018251006054`、`1535262311198101618`、`1535262877219295334`。

## 0DTE Flow 的官方语义

- 🟢 表示 Call，🔴 表示 Put；并不等于确定看涨或看跌。
- `买` 表示 ask 侧主动成交。它无法区分买入开仓、买入平仓或对冲。
- `⚡` 表示 Sweep 的执行紧迫性，不提供可证明的胜率加成；`▣` 为 floor/block，`⇆` 为多腿。
- 当前频道样本中存在显式 `1DTE`，即使官方页面称其为 0DTE 专属，解析器仍以消息中的 DTE 为准，1DTE 永不进入本线。

官方依据：[0DTE Flow Alert](https://docs.yehangshe.com/discord/flow-alert)、[Flow 面板字段](https://docs.yehangshe.com/dashboard/uw-flow)、[Nightwatch 交易框架](https://docs.yehangshe.com/trading-framework)。

2026-08-11 本地快照中，该频道有 52 个消息 ID、45 种去重正文，拆分后得到 49 条独立 alert；一条 Discord 消息可能包含多条 alert，不同消息 ID 也可能在 15–30 秒内重复同一 payload。因此程序先按 `message_id + 子事件` 保留原始记录，再按 payload 指纹做交易窗口幂等。

## v2 决策链

1. Nightwatch `dealer_gex snapshot/history` 提供当前局部 gamma 和节点；至少三次同会话稳定采样。
2. Nightwatch `heatmap snapshot` 只做跨到期结构确认或强冲突否决；缺失、陈旧或降级时保持中性。
3. moomoo SPY 实时 push 构造连续 1 分钟价格行为与 VWAP，并映射到同一 SPX 锚点；Nightwatch 轮询价不生成 K 线。
4. 本地确定性规则寻找节点突破回踩或拒绝反转，并检查当前价仍处于失效位与目标之间。
5. 自动 Flow 只评估已存在的候选：至少两条、在 60/180 秒窗口中达到金额门槛才可确认或强冲突否决；单条、REST 回填、延迟超过 15 秒、显式非 0DTE、来源 ID 不符均不可交易。
6. moomoo 选择唯一当日 PM 结算 SPXW 合约，并以实时 bid/ask、OI、成交量和仓位额度做最终执行门。Nightwatch 的 options/contract 接口仅作为带时间戳的审计证据，OI 被视为结算滞后数据，不作为盘中方向信号。
7. 仅提交 moomoo 模拟单；JUNKMAN 使用独立的状态、备注和日志。

## 退出规则的归因

| 规则 | 来源 |
| --- | --- |
| 结构失效立即退出 | junk_man 策略 |
| 下一次级/大 GEX 节点遇阻退出 | junk_man 策略 |
| 收益达到 +20% 后把保护抬到成本线 | junk_man 明确讨论的工程化实现 |
| -25% 灾难止损 | 工程安全兜底，不是 junk_man 原话 |
| 默认关闭固定止盈 | 避免用任意百分比覆盖结构目标 |
| 15:30 限价退出、15:45 强制退出、无隔夜 | 本项目 0DTE 运行安全规则 |

因此，旧版精确 `-15%/+25%` 不能标注为“垃圾老师策略”；v2 已移除该默认组合。

## Nightwatch API 在模型中的角色

- 已用于实时决策：Dealer GEX snapshot/history、Heatmap snapshot、配额与健康状态。
- 已提供严格客户端和纯证据评估器：chain snapshot、ATM chains、contract intraday、Greeks series、contract volume profile、heatmap cell history、stock state、index OHLC。
- 任何 API 记录必须保留 `as_of` 与本地 `available_at`；未来数据、陈旧数据、状态不允许、合约/到期不匹配或未知 schema 不得被推断成方向。
- API 当前没有可替代 Discord 逐条 0DTE Flow 的 REST 端点；模型也不需要 Flow 才能产生候选。
